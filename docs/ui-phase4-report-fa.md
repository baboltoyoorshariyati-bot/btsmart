# فاز ۴ بازطراحی رابط کاربری — پاک‌سازی CSS مرده و یکسان‌سازی توکن‌ها

**نسخه:** ۱.۱.۱۰ / `37.6.0` (بدون تغییر شماره نسخه) · **شاخه:** `arena/6f0ff475-btsmart`
**دامنه:** فقط ۱۰ فایل CSS لایهٔ نمایش. هیچ کلاس، شناسه، `data-action`، منطق کاری، API یا محاسبه‌ای تغییر نکرد.

---

## ۰) یک جمله

از ۲۳٬۱۵۸ اعلان CSS، **۱٬۳۵۵ اعلان مرده** (در ۲۳۹ قاعده) حذف شد و **۲۹ رنگ خام** با توکن‌های `--bt-*` جایگزین شد؛ در نتیجه ۳۴٬۵۶۵ بایت (۴.۳٪) از حجم CSS کم شد، **بدون تغییر ظاهر** — و این «بدون تغییر» با یک اثبات ماشینی و نه با چند اسکرین‌شات، سنجیده شده است.

> **چرا اسکرین‌شات ندارد؟** این تغییر به‌طور اثباتی هیچ مقدار محاسبه‌شده‌ای را عوض نمی‌کند؛ اثباتش از اسکرین‌شات قوی‌تر است (بند ۳). علاوه بر آن، مرورگر تست (Chromium) در این نشست در محیط اجرا نصب نبود و نصب آن از مسیر اینترنت در دسترس نیست. اگر تصویر «قبل/بعد» می‌خواهید، در نشست بعد همان ۹ صفحه/عرض را می‌گیرم؛ خروجی باید پیکسل‌به‌پیکسل یکسان باشد.

## ۱) روش کار

اکثر فایل‌های CSS این پروژه طی نسخه‌ها **لایه‌روی** شده‌اند؛ قاعدهٔ تازه‌تر همان انتخابگر را با مقدار جدید بازنویسی می‌کند و قاعدهٔ قدیمی «مرده» می‌ماند. برای پیدا کردن دقیق آنها:

1. یک تجزیه‌گر CSS با **آفست دقیق کاراکتر** نوشتم (`/tmp/css/parse.mjs`) که کامنت‌ها، رشته‌ها، `@media` و `@supports` را درست می‌شناسد و بدنهٔ `@keyframes` / `@font-face` / `@page` را کنار می‌گذارد (اعلان‌های داخل این‌ها اصلاً آبشاری نیستند؛ تحلیل سادهٔ متنی این‌جا ۷۴۰ مورد را اشتباه می‌شمرد).
2. برای هر اعلان کلید آبشاری ساختم: `(media, selector, property, !important)`.
3. اعلانی «مرده» است اگر **بعد از آن** در همین زنجیره (۱۰ فایل به ترتیب بارگذاری) اعلانی با همان کلید بیاید. چون انتخابگر و media عیناً یکی‌اند، ویژگی (specificity) یکی است و «آخری» همیشه برنده است؛ حذف اعلان‌های قبلی هیچ‌وقت مقدار نهایی را عوض نمی‌کند.
4. حذف با همان آفست‌ها انجام شد (نه با regex روی متن)، تا قالب‌بندی و بقیهٔ اعلان‌ها دست‌نخورده بماند. قاعده‌ای که همهٔ اعلان‌هایش مرده بود، کامل حذف شد.

## ۳) اثبات: ظاهر عوض نشده (قابل بازتولید)

ابزار تازه‌ای در مخزن اضافه شد:

```bash
node scripts/verify-css-cascade.js            # مقایسهٔ دیسک با HEAD
node scripts/verify-css-cascade.js <git-ref>  # مقایسه با هر مرجع دیگر
```

این ابزار «نقشهٔ آبشاری» هر دو نسخه را می‌سازد (آخرین مقدار برنده برای هر `(media, selector, property, !important)` در کل زنجیرهٔ ۱۱ فایل) و آنها را مقایسه می‌کند. خروجی اجرای واقعی روی همین تغییر:

```json
{
 "declarations": { "before": 23158, "after": 21803 },
 "important":    { "before": 4110,  "after": 3962  },
 "cascadeKeys":  { "before": 21781, "after": 21781 },
 "rules":        { "before": 7038,  "after": 6799  },
 "differences":  { "missing": 0, "changed": 0, "added": 0, "orderProblems": 0 }
}
```

یعنی برای هر ۲۱٬۷۸۱ ترکیب `(media, selector, property, !important)`، مقدار نهایی **مو‌به‌مو** همان قبلی است، و ترتیب قاعده‌ها هم حفظ شده. چون مرورگر برای هر عنصر همان اعلان‌های برنده را می‌بیند، **هیچ عنصری نمی‌تواند ظاهر متفاوتی بگیرد**. (اجرای فاز ۴ با نسخه‌ای از این ابزار بود که `var(--bt-*)` را به مقدار هگز بازحل می‌کرد؛ از فاز ۵ به بعد خودِ ابزار سخت‌گیرانه‌تر شد: مقایسهٔ خامِ «متن اعلان برنده»، بدون هیچ نرمال‌سازی — به [`ui-phase5-report-fa.md`](ui-phase5-report-fa.md) بند ۳.)

جدا از این، برای مرحلهٔ توکن یک بررسی دوم هم انجام شد: اگر در فایل‌های نهایی هر `var(--bt-*)` را با مقدارش جایگزین کنیم، **بایت‌به‌بایت** همان فایل قبل از مرحلهٔ توکن می‌شود (`OK — all files resolve back to the pre-token bytes exactly`).

## ۴) یکسان‌سازی توکن‌ها (بخش اول)

۳۲ توکن `--bt-*` وجود دارد که هر کدام **فقط یک‌بار و فقط در `:root`** تعریف شده‌اند. در ۵ فایل، ۲۹ رنگ هگزِ خام که دقیقاً با یکی از این توکن‌ها برابر بود با `var(--توکن)` جایگزین شد:

| توکن | تعداد جایگزینی | فایل‌ها |
|---|---:|---|
| `--bt-soft` | ۱۱ | styles، design، theme، warehouse-document |
| `--bt-brand` | ۷ | styles، design، compatibility |
| `--bt-bg` | ۳ | styles |
| `--bt-panel-2` | ۲ | styles، compatibility |
| `--bt-amber-bg`، `--bt-amber`، `--bt-purple-bg`، `--bt-red`، `--bt-green`، `--bt-brand-50` | ۶ | theme، compatibility، design |

شرط ایمنی: توکن باید **یک‌بار** در `:root` تعریف شده باشد و **هیچ‌جا بازتعریف نشود** (وگرنه ممکن است در یک محدودهٔ خاص مقدار دیگری داشته باشد). رنگ‌های سفید/سیاه خام عمداً دست نزده ماندند تا رگرسیون تست‌ها و خوانایی diff حفظ شود.

**آنچه در فاز بعد می‌ماند:** ۱۵۱ متغیر سفارشی در کل پروژه هست که ۳۲ تای آن‌ها در بیش از یک فایل تعریف شده‌اند (`--brand`/`--bt-brand`، `--ink`/`--bt-ink`، `--muted`/`--bt-muted` و…). یکی‌کردن این دو خانواده اسم‌ها، تغییر مقدار در بعضی محدوده‌ها را ممکن می‌کند و باید با تأیید بصری انجام شود.

## ۵) ۷ اعلانی که عمداً حذف نشدند

پنج تستِ این مخزن، CSS را به‌صورت **متنی** قفل می‌کنند (regex روی متن فایل، نه روی نتیجهٔ رندر). حذف این اعلان‌ها هرچند از نظر آبشاری بی‌اثر است، آن تست‌ها را می‌شکند. برای اینکه در این فاز **هیچ تستی تغییر نکند**، این ۷ مورد دست‌نخورده ماندند:

| فایل | انتخابگر | اعلان | تست |
|---|---|---|---|
| `form-layout.css` | `#appView #content .bt-customer-field` | `height:38px!important` | `tests/customer-compact-layout.test.js` |
| `form-layout.css` | `#appView #content .sd-oe-customer` | `padding:8px 14px!important` | `tests/form-layout.test.js` |
| `theme.css` | `#appView .rail` | `background:linear-gradient(180deg,var(--bt-rail-red) …)` | `tests/rail-clock-bell.test.js` |
| `theme.css` | `#appView #railNav > button[aria-current="page"]` | `background:#fff!important` | `tests/rail-clock-bell.test.js` |

**پیشنهاد فاز بعد:** این ۵ تست به‌جای «متن فایل» روی «نقشهٔ آبشاری» نوشته شوند (همان تابع `scripts/verify-css-cascade.js`)؛ بعد این ۷ اعلان هم بدون هیچ ریسکی حذف می‌شوند.

## ۶) کاهش واقعی `!important` — چرا کامل نشد

۷۵٪ بار `!important` در سه فایل است: `compatibility.css` (۱٬۵۲۲)، `theme.css` (۱٬۲۵۷)، `form-layout.css` (۴۷۲). حذف `!important` از یک اعلان **برنده** را نمی‌توان بدون رندر واقعی امن دانست: ممکن است قاعده‌ای در لایهٔ دیگر با ویژگی کمتر آن را نگه داشته باشد و با حذف `!important` همان مقدار به‌هم بریزد. بنابراین در این فاز فقط `!important`های **مرده** حذف شدند (−۱۴۸ مورد) و کاهش بیشتر به فاز ۵ با آزمون بصری در ۴ عرض موکول شد؛ نقشهٔ کار همان است: حذف دسته‌ای از `compatibility.css`، سپس `theme.css`، با اسکرین‌شات مرجع ۹ صفحه/عرض.
